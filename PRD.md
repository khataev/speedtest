# Требования к MVP утилиты Speedtest

## Цель

Speedtest — консольная утилита для оценки скорости скачивания с конкретного HTTP(S)-сервера. Пользователь указывает прямой URL конечного файла и получает один итоговый отчёт со средним временем запроса, суммарным объёмом и скоростью скачивания.

На реализацию MVP отведено 1–2 часа.

## Поведение CLI

Команда запуска — `node speedtest.mjs <url>`. Единственный ключ — `--help`, который выводит справку и завершает программу без сетевых запросов. Принимается один абсолютный URL с протоколом `http:` или `https:`.

- Успешный прогон состоит ровно из 10 последовательных GET к одному и тому же URL с исходными параметрами. Следующая попытка начинается после полного чтения предыдущего ответа. Успешный ответ — `200 OK` с непустым телом.

- При любом HTTP-статусе, отличном от `200`, пустом или оборванном теле, сетевой ошибке или таймауте прогон останавливается на текущей попытке. В `stderr` выводятся номер попытки и причина. Код выхода ненулевой. Итог появляется только после десяти успешных попыток.

- Для прогона используется один агент с keep-alive. Пока сервер держит сокет открытым, следующие запросы могут его переиспользовать. Если нужен новый сокет, действует фиксированный лимит в 10 секунд на DNS, TCP и, для HTTPS, TLS. После установки соединения этот лимит перестаёт действовать. Отдельного таймаута на ожидание ответа и чтение тела в MVP нет.

## Методика измерения

Длительность попытки измеряется монотонными часами от запуска GET до полного чтения тела. В неё входит ожидание ответа сервера и, при новом соединении, его установка. Длительность первой попытки учитывается наравне с остальными.

Объём определяется по фактически прочитанным байтам тела. HTTP-сжатие учитывается в том виде, в котором тело получено, до распаковки. Заголовки и служебные данные HTTP, TLS и TCP в подсчёт не входят. Тело читается частями, поэтому суммарный размер файла не определяет расход памяти. Для подсчёта достаточно прочитать тело, `Content-Length` необязателен.

- **Среднее время запроса** — сумма длительностей успешных попыток, делённая на 10. В отчёте отображается в секундах.

- **Суммарный объём** — сумма прочитанных байтов, отображается в десятичных МБ.

- **Скорость** — суммарное число битов, делённое на сумму длительностей запросов в секундах. Для вывода в Мбит/с результат делится на 1 000 000.

Например, 50 МБ (400 Мбит) за 4 секунды суммарного времени дают 100 Мбит/с и среднее время запроса 0,4 с при 10 попытках. Результат характеризует скачивание с указанного сервера при этой последовательности запросов.

## Архитектура и компромиссы

Основной артефакт для распространения — один файл `speedtest.mjs`. Используем Node.js 24+, JavaScript с ESM, JSDoc для контрактов, `node:util.parseArgs` для CLI и `node:http` / `node:https` для сети. Скрипт запускается без установки пакетов и сборки.

Скрипт построен с учетом принципов чистой архитектуры с начальным выделением компонентов под конкретный слой (бизнес правила, контролер, пользовательский интерфейс итд): 

- **`calculateBitsPerSecond({ bytes, durationMs })`** — чистая функция, которая возвращает скорость в битах в секунду для одной пары «объём и длительность».

- **`downloadOnce`** — HTTP(S)-адаптер одного запроса. Следит за установлением соединения, измеряет время и считает байты. Возвращает `Promise<{ bytes, durationMs }>`.

- **`measureRepeatedDownloads(url, output)`** — интерактор серии из 10 запросов. Напрямую вызывает `downloadOnce`, агрегирует байты и длительности, вычисляет среднее время запроса и публикует итог через `output.onComplete(result)`. Результат содержит `totalBytes`, `averageRequestDurationMs` и `bitsPerSecond`. Интерактор дожидается завершения вывода.

- **`reportSuccess, reportError, reportProgress`** — адаптер вывода. Форматирует итог для консоли. Адаптер записи в файл сможет принимать тот же результат.

- **`main(argv)`** — CLI-контроллер и точка сборки. Разбирает аргументы, передаёт URL интерактору, переводит ошибки в сообщения и код выхода.

**Компромисс с чистой архитектурой.** Интерактор напрямую вызывает HTTP(S)-адаптер. Для одного способа скачивания достаточно выделить границы ответственности между функциями. При появлении нескольких взаимозаменяемых реализаций прямой вызов можно заменить передачей функции. Правила агрегации серии принадлежат интерактору, а формула скорости остаётся независимой от транспорта и способа сбора измерений.

## Критерии приёмки

Приёмка ручная. Проверяем `--help`, обработку неверного URL, ровно 10 последовательных GET при успехе, единственный итог с тремя метриками и ненулевой код выхода с понятной диагностикой при ошибке.

## Расширения после MVP

Из возможных улучшений можно рассмотреть:

- обработку редиректов при скачивании файла
- замену консольного интерфейса более симпатичным TUI
- Более частый апдейт о текущем объеме и трафике
- Нормирование времени прохождения теста под любое соединение. Сейчас - чем медленнее соединение, тем дольше будет идти тест на одном и том же файле. Вместо этого можно взять файл побольше в несколько Гб и скачивать его  в течение определенного времени с ограничением по времени.
- поддержку других протоколов ((s)FTP, WebDav, WebSockets, ...)
- измерение исходящей скорости (нужен сервер, позволяющий загружать файлы или эмулировать их загрузку)
- c усложнением логики можно добавлять тесты, можно рассмотреть специализированные библиотеки для организации CLI, переход на TypeScript, выделение отдельных компонентов и упаковку в SEA бинарник
